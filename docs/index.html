Version Control Framework for Jujutsu (jj)

Structured forms, dry-run guardrails, and calibrated machine decisions on top of Jujutsu.

Jujutsu gives engineers stable Change IDs, anonymous branches, algebraic conflicts, and an undoable operation log. jjr turns those primitives into a coherent library and interactive workspace—combining deterministic graph invariants, TypeSafe AI's Jev decision model for fast calibrated judgment, and a light LLM layer reserved strictly for naming and prose.

Engine: jj --at-op ... --no-integrate-operation System One: TypeSafe Jev (/v1/systemone) System Two: Light LLM Narrator
01

Architecture

jjr is organized around a strict separation between hard invariants (deterministic rules that never bend), fast calibrated judgment (TypeSafe Jev evaluating parallel typed questions over a single diff state), and prose generation (a lightweight LLM called only when a human needs a title, bookmark slug, or explanation). Every graph rewrite executes first as an uncommitted Jujutsu dry-run operation inside jj-graph, so you see the real resulting DAG—conflicts and auto-rebases included—before touching the operation log or working copy.

02

Identity–State Separation & Graph Model

In Jujutsu, a ChangeId (reverse-hex letters k–z) identifies a logical unit of work across every rebase, squash, and amendment. A CommitId (hex 0–9a–f) identifies one immutable point-in-time snapshot underneath it. Mixing them up causes fragile scripts and agent retries that target stale commits. jjr brands both at the TypeScript type boundary (jjr/index.d.ts) and validates them at runtime.

Two Zones & Dual Time Axes

JjrGraph partitions every loaded revision into immutable (shared bedrock such as trunk() and tags) or mutable (local work you can freely rewrite). Before anything rewrites the graph, a pre-flight check resolves trunk() and immutable_heads() (whose default is trunk() | tags() | untracked_remote_bookmarks() | untracked_remote_tags()): an unresolvable boundary blocks every rewrite, and ::trunk() stays bedrock even when immutable_heads() was overridden without it. Recovery operates across two orthogonal time axes: the repository-wide Operation Log (jj op restore) and per-change Evolution Log (jj restore --from <commit> --to <change>, or an offset such as --from lnv/1), preferring surgical single-change recovery whenever sibling arms have independent edits. In jj-graph, a change's Evolution sheet dry-runs that restore for any earlier version.

Every mutable change should be one of the reference's canonical shapes, and JjrGraph.classifyShape() reports which one the mutable zone is in, together with its publishing rule:

ShapeOptimal DAGPublishing boundary
singleOne change rooted at trunk()One bookmark, or jj git push -c @- when ready
stackShallow linear stack, bottom-up by stability (DEEP_STACK past 6)Publish bottom layers once independently reviewable; keep drafts local
parallelSibling arms off trunk()Independent bookmarks / PRs that land in any order
megamergeArms joined by a local octopus merge + empty @Never push the megamerge; push the arms
restingA single empty @ atop trunk()Nothing to publish

TypeSafe Jev (System One) Integration

Jev is TypeSafe AI's non-autoregressive System One decision model (POST /v1/systemone). Rather than streaming tokens and begging a chat model for valid JSON, jjr sends a single structured state and evaluates multiple typed questions in parallel—receiving calibrated probabilities and confidence scores at roughly 40–200× the speed and a fraction of the cost of frontier LLMs.

  • Single-Pass Change Triage (triageChange): Batches 5 questions in one call: intent (choice), structural/behavioral entangled (noul), publishReadiness (score), hasDebugOrSecrets (noul), and apiWithoutConsumer (noul: a new API with no caller or test, against the rule to pair every new API with a consumer).
  • Two-Part Dependency Gate (assessDependency): Runs two parallel noul propositions—Causal Necessity and Independent Reviewability. When either probability lands inside the ambiguous band (0.28–0.72), jjr pauses to confirm with the developer instead of guessing.
  • Behind-the-Scenes Guardrail Augmentation (evaluateActionRisk): Catches unmarked local scratchpads before a push and scores blast radius to recommend dry-run previews automatically.
  • Recovery & Absorb Routing (recommendRecovery, routeHunk): Chooses surgical evolog restore vs. repo-wide op restore, and ranks candidate feature arms when a working-copy fixup atop a megamerge has ambiguous ownership.
import { JevClient, JjrJevAssistant, choice, noul, score } from './jjr/index.mjs';

const jev = new JjrJevAssistant(new JevClient({
  // Reads process.env.TYPESAFE_API_KEY automatically; defaults to https://api.typesafe.ai
  // Also accepts an existing @typesafe-ai/sdk client via { sdkClient }
  defaultModel: 'jev-latest',
}));

const { answers } = await jev.triageChange({
  changeId: 'tzpzvowk',
  description: 'refactor: extract session validator',
  touchedPaths: ['src/auth/session.ts'],
  diffExcerpt: '...',
});
// answers.intent.choice          -> 'structural' (confidence: 0.91)
// answers.entangled.noul         -> 0.14
// answers.publishReadiness.legend -> 'ready-to-land' (score: 2.86)
04

Guardrail Pipeline

Every mutation, bookmark, push, Git interop command, and workspace action passes through JjrGuardrailPipeline before touching the repository—including every step of jj-graph's POST /api/dry handler, where the revisions a command rewrites are resolved by jj itself. jjr/commands.mjs knows what each command does to the revisions it names: jj new X only reads X, jj new -B X rewrites it, jj new -A X rewrites its children, and jj squash --into X rewrites X. Blockers always include a concrete remediation command rather than a dead-end error.

  1. PreflightGuard: blocks every rewrite while trunk() or immutable_heads() does not resolve; warns when shared history is unprotected.
  2. ImmutableBedrockGuard: never rewrites immutable() (or ::trunk()), and refuses --ignore-immutable outright.
  3. DivergenceGuard: halts stacking, bookmarking and pushing while divergent() is non-empty, even for jj new; abandon, converge, metaedit --update-change-id and op restore stay open.
  4. MegamergeFence: hard-blocks pushing or bookmarking any range that contains a local composition merge.
  5. PublishingGate: before a bookmark or a push, every revision in the range is conflict-free, non-empty (merges and blueprints excepted), formatted (jj fix), and green (jj run). Known failures block both; unverified snapshots block a push and warn on a bookmark.
  6. ColocatedGitGuard: jj is the only writer; only read-only git (log, show, diff, status, listing branch/tag…) passes, and everything else gets its jj equivalent.
  7. WorkspaceDisciplineGuard: workspaces are for parallel agents, test suites and builds, never for switching branches.
  8. ChangeIdAddressingGuard: warns when mutable work is named by its rotating commit id instead of its change id.

Self-Evident SDLC Patterns

Rather than memorizing flags, jjr exposes opinionated pattern builders in jjr/patterns.mjs. Each recipe emits both human-readable commands and structured argument arrays that preview safely inside jj-graph's dry-run engine.

Tidy First? (Structural Below Behavioral)

JjrPatterns.tidyFirstBelow()

Slip zero-behavior-change cleanup underneath active feature work so reviewers can approve mechanical refactors separately and revert behavioral changes cleanly.

jj new -B kmpqrstu -m "refactor: extract rate limiter seam"
# If already mixed in one change:
jj split -r kmpqrstu

Characterization Tests Before Refactors

JjrPatterns.characterizationTestsBelow()

Before restructuring untested code, slip a test-only change below the refactor so reviewers and CI see existing behavior locked down before anything moves.

jj new --no-edit -B kmpqrstu -m "test: characterize rate limiter"
jj run --ignore-changes -r 'kmpqrstu- | kmpqrstu' -- npm test

TDD Red-Test Verification

JjrPatterns.verifyRedTest()

Prove a new test actually fails without its implementation. jj split --parallel keeps the change id on the selected implementation files and moves @ to a tests-only sibling; once the run is red, the tests fold back into the implementation, so the change keeps its id and no red commit stays in the DAG.

jj split --parallel -m "feat: ledger totals" src/billing/ledger.ts
jj run --ignore-changes -r @ -- npm test                  # confirm red
jj squash --from @ --into kmpqrstu --use-destination-message
jj edit kmpqrstu

Parallel Change & Isolated Activation

expandContract() · isolateActivation()

Breaking changes expand, migrate, then contract, each buildable on its own. User-facing activation is a tiny top-level change on top of dark plumbing, so an emergency rollback reverts one switch (ACTIVATION_NOT_ON_TOP catches work stacked above it).

jj new trunk() -m "feat: expand user id with uuid"
jj new -m "refactor: migrate user id callers to uuid"
jj new -m "chore: contract user id, remove int"
jj new zyxwvuts -m "feat: activate new-billing"   # on top of the plumbing

Local Octopus Megamerge + jj absorb

localMegamerge() · absorbFixups() · extractSharedPrimitive()

Test independent feature arms together without coupling their histories. MegamergeFence ensures the local merge can never leak to a remote; jj absorb (assisted by Jev's hunk router when ambiguous) flows fixups back to their owning arms, and MEGAMERGE_NOT_EMPTY catches edits made in the merge itself. When composition reveals a primitive both arms need, it becomes a common ancestor beneath them instead of stacking one arm on the other.

jj new arm_a arm_b arm_c -m "local: dev megamerge"
jj new
jj absorb                              # jj absorb --from <megamerge> if it was edited directly
jj new --no-edit -B arm_a -B arm_b -m "feat: shared parser"
jj squash --from @ --into 'arm_a- & arm_b-' src/parse.ts

Clean Conflict Resolution

JjrPatterns.resolveConflictCleanly()

Resolve in a child commit so the resolution is reviewable on its own, then fold it down; it propagates to every descendant. CONFLICTED_CHANGE suggests the fold as soon as a non-conflicted child exists.

jj new pqrstuvw
jj resolve        # or edit the markers
jj diff           # inspect exactly the resolution
jj squash

Stack Validation & Layered Publishing

stackValidation() · JjrRunner.planLayeredPublish()

Before publishing, format every mutable revision and build and test each one on its own. jj-graph's Verify stack does both as operations it never keeps (POST /api/jjr/verify; set the command with --verify-command or jj config set --repo jjr.verify-command 'npm test'). The Publishing Gate then reads those results: Plan publishing marks the green bottom layers publishable and keeps the rest local.

jj fix -s 'roots((trunk()..@) & mutable())'
jj run --ignore-changes -r '(trunk()..@) & mutable()' -- npm test
jj git push -c kmpqrstu    # only the layers the gate passed

Branch by Abstraction & Post-Merge Convergence

branchByAbstraction() · postMergeConvergence()

Swap subsystems across 5 independently buildable revisions (seam → dark implementation → isolated activation switch → remove legacy → optional contract), then converge landed work back onto trunk(). jj 0.47 takes several revisions for -s without the old all: prefix; --skip-emptied collapses changes whose diffs already landed. ROOT_BEHIND_TRUNK flags arms still based on an old trunk.

jj git fetch
jj rebase -s 'roots(trunk()..@)' -o 'trunk()' --skip-emptied

Authoring Loops & Agent Workspaces

squashWorkflow() · editWorkflow() · composeAgentWorkspaces()

Describe first and flush hunks down from an empty @ (squash workflow), or edit a change in place and insert newly found prerequisites below it (edit workflow). Parallel agents each get a jj workspace; the orchestrator composes their working copies in one local megamerge.

# squash workflow
jj describe -m "feat: retry budget"
jj new
jj squash
# edit workflow
jj edit kmpqrstu
jj new -B @ -m "refactor: extract clock"
jj next --edit
# agent workspaces
jj new agent-a@ agent-b@ -m "local: agents megamerge"

Show HN: jjr – Guardrails, dry-run patterns, and System-One decisions on top of Jujutsu (jj)

Git trained an entire generation of engineers (and now coding agents) to treat version control as an append-only tape of chronological accidents. Even after adopting Jujutsu (jj)—which gives us stable Change IDs, anonymous branches, first-class algebraic conflicts, and an undoable operation log—most humans and agents still use jj like Git with shorter flags. They stack unrelated features linearly, accidentally push local integration merges, mix structural refactors with behavioral changes, and burn frontier-LLM calls just to classify a diff.

We built jjr, an opinionated framework library and visual workspace on top of jj (integrated directly with jj-graph's dry-run engine) that turns Jujutsu's raw graph primitives into self-evident patterns, pre-flight guardrails, and calibrated active feedback.

1. Identity–State Separation. Branded ChangeId (reverse-hex k–z) and CommitId (hex 0–9a–f) types catch stale-SHA bugs immediately.

2. Real Dry-Run Guardrails. Every rewrite previews via jj --at-op <tip> --no-integrate-operation and passes through eight hard rules (Pre-flight, Immutable Bedrock, Divergence Guard, Megamerge Fence, Publishing Gate, Colocated Single-Writer Guard, Workspace Discipline, Change-ID Addressing) before touching disk. The Publishing Gate reads real results: jj fix and jj run verify every layer, and only the green bottom of a stack gets published.

3. TypeSafe Jev (System One) + Light LLM (System Two). Fast, non-autoregressive calibrated decisions (choice, score, noul) power change triage, the Two-Part Dependency Gate (pausing for human confirmation in the ambiguous probability band), blast-radius advisories, surgical evolog recovery routing, and hunk routing. A lightweight LLM only runs when prose is needed for commit titles and summaries.

4. Portable TUI/GUI ViewModels & Agentic Evals. Render-agnostic ViewModels port 1:1 to terminal ANSI or web/desktop UIs, validated by a 15-scenario eval harness over real throwaway jj repositories.

Git made rebasing scary. Jujutsu made rebasing fearless. jjr makes clean graph discipline—and calibrated machine assistance—the path of least resistance.
