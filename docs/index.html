Version Control Framework for Jujutsu (jj)

Structured forms, dry-run guardrails, and calibrated machine decisions on top of Jujutsu.

Jujutsu gives engineers stable Change IDs, anonymous branches, algebraic conflicts, and an undoable operation log. jjr turns those primitives into a coherent library and interactive workspace—combining deterministic graph invariants, TypeSafe AI's Jev decision model for fast calibrated judgment, and a light LLM layer reserved strictly for naming and prose.

Engine: jj --at-op ... --no-integrate-operation System One: TypeSafe Jev (/v1/systemone) System Two: Light LLM Narrator
01

Architecture

jjr is organized around a strict separation between hard invariants (deterministic rules that never bend), fast calibrated judgment (TypeSafe Jev evaluating parallel typed questions over a single diff state), and prose generation (a lightweight LLM called only when a human needs a title, bookmark slug, or explanation). Every graph rewrite executes first as an uncommitted Jujutsu dry-run operation inside jj-graph, so you see the real resulting DAG—conflicts and auto-rebases included—before touching the operation log or working copy.

02

Identity–State Separation & Graph Model

In Jujutsu, a ChangeId (reverse-hex letters k–z) identifies a logical unit of work across every rebase, squash, and amendment. A CommitId (hex 0–9a–f) identifies one immutable point-in-time snapshot underneath it. Mixing them up causes fragile scripts and agent retries that target stale commits. jjr brands both at the TypeScript type boundary (jjr/index.d.ts) and validates them at runtime.

Two Zones & Dual Time Axes

JjrGraph partitions every loaded revision into immutable (shared bedrock such as trunk() and tags) or mutable (local work you can freely rewrite). Recovery operates across two orthogonal time axes: the repository-wide Operation Log (jj op restore) and per-change Evolution Log (jj restore --from <commit> --to <change>), preferring surgical single-change recovery whenever sibling arms have independent edits.

03

TypeSafe Jev (System One) Integration

Jev is TypeSafe AI's non-autoregressive System One decision model (POST /v1/systemone). Rather than streaming tokens and begging a chat model for valid JSON, jjr sends a single structured state and evaluates multiple typed questions in parallel—receiving calibrated probabilities and confidence scores at roughly 40–200× the speed and a fraction of the cost of frontier LLMs.

  • Single-Pass Change Triage (triageChange): Batches 4 questions in one call: intent (choice), structural/behavioral entangled (noul), publishReadiness (score), and hasDebugOrSecrets (noul).
  • Two-Part Dependency Gate (assessDependency): Runs two parallel noul propositions—Causal Necessity and Independent Reviewability. When either probability lands inside the ambiguous band (0.28–0.72), jjr pauses to confirm with the developer instead of guessing.
  • Behind-the-Scenes Guardrail Augmentation (evaluateActionRisk): Catches unmarked local scratchpads before a push and scores blast radius to recommend dry-run previews automatically.
  • Recovery & Absorb Routing (recommendRecovery, routeHunk): Chooses surgical evolog restore vs. repo-wide op restore, and ranks candidate feature arms when a working-copy fixup atop a megamerge has ambiguous ownership.
import { JevClient, JjrJevAssistant, choice, noul, score } from './jjr/index.mjs';

const jev = new JjrJevAssistant(new JevClient({
  // Reads process.env.TYPESAFE_API_KEY automatically; defaults to https://api.typesafe.ai
  // Also accepts an existing @typesafe-ai/sdk client via { sdkClient }
  defaultModel: 'jev-latest',
}));

const { answers } = await jev.triageChange({
  changeId: 'tzpzvowk',
  description: 'refactor: extract session validator',
  touchedPaths: ['src/auth/session.ts'],
  diffExcerpt: '...',
});
// answers.intent.choice          -> 'structural' (confidence: 0.91)
// answers.entangled.noul         -> 0.14
// answers.publishReadiness.legend -> 'ready-to-land' (score: 2.86)

Guardrail Pipeline

Every mutation, push, Git interop command, and workspace action passes through JjrGuardrailPipeline before touching the repository—including inside jj-graph's POST /api/dry handler. Blockers always include a concrete remediation command rather than a dead-end error.

05

Self-Evident SDLC Patterns

Rather than memorizing flags, jjr exposes opinionated pattern builders in jjr/patterns.mjs. Each recipe emits both human-readable commands and structured argument arrays that preview safely inside jj-graph's dry-run engine.

Tidy First? (Structural Below Behavioral)

JjrPatterns.tidyFirstBelow()

Slip zero-behavior-change cleanup underneath active feature work so reviewers can approve mechanical refactors separately and revert behavioral changes cleanly.

jj new -B kmpqrstu -m "refactor: extract rate limiter seam"
# If already mixed in one change:
jj split -r kmpqrstu

TDD Red-Test Verification

JjrPatterns.verifyRedTest()

Prove a new test actually fails without its implementation by lifting implementation files into a parallel sibling, running the test suite, and folding them back into a single green commit.

jj split --parallel src/billing/ledger.ts
npm test                      # confirm red
jj squash --from @+ --into @  # restore single green node

Local Octopus Megamerge + jj absorb

JjrPatterns.localMegamerge()

Test independent feature arms together without coupling their histories. MegamergeFence ensures the local merge can never leak to a remote; jj absorb (assisted by Jev's hunk router when ambiguous) flows fixups back to their owning arms.

jj new arm_a arm_b arm_c -m "local: dev megamerge"
jj new
jj absorb

Branch by Abstraction & Post-Merge Convergence

branchByAbstraction() · postMergeConvergence()

Swap subsystems across 5 independently buildable revisions (seam → dark implementation → isolated activation switch → remove legacy → optional contract), then converge landed work back onto trunk().

jj git fetch
jj rebase -s 'all:roots(trunk()..@)' -o trunk()

Agentic Evals Blueprint

Show HN: jjr – Guardrails, dry-run patterns, and System-One decisions on top of Jujutsu (jj)

Git trained an entire generation of engineers (and now coding agents) to treat version control as an append-only tape of chronological accidents. Even after adopting Jujutsu (jj)—which gives us stable Change IDs, anonymous branches, first-class algebraic conflicts, and an undoable operation log—most humans and agents still use jj like Git with shorter flags. They stack unrelated features linearly, accidentally push local integration merges, mix structural refactors with behavioral changes, and burn frontier-LLM calls just to classify a diff.

We built jjr, an opinionated framework library and visual workspace on top of jj (integrated directly with jj-graph's dry-run engine) that turns Jujutsu's raw graph primitives into self-evident patterns, pre-flight guardrails, and calibrated active feedback.

1. Identity–State Separation. Branded ChangeId (reverse-hex k–z) and CommitId (hex 0–9a–f) types catch stale-SHA bugs immediately.

2. Real Dry-Run Guardrails. Every rewrite previews via jj --at-op <tip> --no-integrate-operation and passes through six hard rules (Immutable Bedrock, Divergence Guard, Megamerge Fence, Publishing Gate, Colocated Single-Writer Guard, Workspace Discipline) before touching disk.

3. TypeSafe Jev (System One) + Light LLM (System Two). Fast, non-autoregressive calibrated decisions (choice, score, noul) power change triage, the Two-Part Dependency Gate (pausing for human confirmation in the ambiguous probability band), blast-radius advisories, surgical evolog recovery routing, and hunk routing. A lightweight LLM only runs when prose is needed for commit titles and summaries.

4. Portable TUI/GUI ViewModels & Agentic Evals. Render-agnostic ViewModels port 1:1 to terminal ANSI or web/desktop UIs, validated by a 12-scenario eval harness over real throwaway jj repositories.

Git made rebasing scary. Jujutsu made rebasing fearless. jjr makes clean graph discipline—and calibrated machine assistance—the path of least resistance.
